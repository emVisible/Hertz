# D-233 媒体时长必须问「哪一条流」，不能问容器

- 日期：2026-10-19 · 状态：已采纳

## 结论

凡按「画面长度」算 offset、排字幕、抽帧、定补齐长度的地方，一律问**视频流时长**
（`probe_video_duration`），不问容器时长。`ffprobe` 的容器时长取**最长那条流**（通常是音频），
素材「音频比画面长」是常态——拿它当画面长度用，四处都算错。

## 背景

2026-10-19 用户合集成片后半段黑屏（详见 CHANGELOG「合集成片后半段黑屏」）。
实测同一组素材：修复前容器 89.62s / 视频流 45.67s，t≥60s 视频包 **0 个**；
修复后视频流 81.70s，t≥60s 视频包 651 个。事故素材
`data/pipeline/2026-10-11-01/raw.mp4`：视频 14.7s / 音频 22.7s。
全库扫描 `data/media/videos`：一批素材音频比画面长 0.6–4.6s，事故条差 8s——**不是单例**。

四处中招（各有各自的「不报错」形态）：

| 位置 | 形态 |
|---|---|
| `assemble` | xfade offset 过了已拼画面后**停止延长视频而不报错** → 黑屏 |
| `cover` | 抽帧点越过末帧 → 黑封面（文件正常） |
| `phash` | 25% seek 越过末帧 → 哈希静默变 None |
| `compose` | 原声轨没 atrim 到 target → 成片「短画面 + 长音频」，字幕排进无画面的时段 |

## 选项与取舍

- **选了**：新增 `probe_video_duration`（视频流缺失时回退容器时长），四处全部改按视频流；
  `assemble` 的产物校验改盯视频流（`_VIDEO_TOLERANCE_S=1.0`）。
- **没选**「compose 末尾加 `-shortest`」：短片段会被硬剪掉尾帧，且掩盖而非修复；
  `assemble` 的黑尾巴正是这么静默通过的——校验要看见缺陷，不能替缺陷打掩护。
- **没选**「只修 assemble 一处」：同族问错发生在四个位置，只修一处是把同一把刀留给另外三个房间。

## 判据

- `tests/test_producer_assemble.py` 端到端断言**修复后 t≥60s 视频包 651**、音画等长、
  校验遇视频流短缩必抛 `ProducerError`
- `tests/test_media_stream_duration.py`（9 条）：封面 6 次抽样全部非黑
  （旧行为 6 连对概率 ≈ 0.2⁶，不会侥幸绿）、哈希必可算、成片两条流之差 ≤ 1s

## 代价

- 画面 < 音频的素材成片**总长变短**（音频被钉到画面长度）。这是有意为之的语义：
  宁可短一截，不留黑尾巴。
- 「视频流缺失时回退容器」意味着纯音频输入仍按容器——回退路径自身没有单判据，靠上层语义兜住。
